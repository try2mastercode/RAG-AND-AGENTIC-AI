Why a vector DB sits in front of an LLM

An LLM has no memory of your documents. RAG fixes that by searching a vector database for relevant chunks first, then handing only those chunks to the model:

1

Text → embedding

Every document was embedded once with all-MiniLM-L6-v2 and stored in an HNSW graph index inside Chroma.

→
2

Query → nearest neighbors

Your question is embedded the same way, then Chroma walks the HNSW graph for the closest vectors by cosine distance.

→
3

Filters narrow the graph search

where (metadata) and where_document (substring) filters are applied so only matching candidates are considered.

→
4

Retrieved chunks → Groq

The top-k passages are stuffed into a prompt so Groq's LLM answers using only what was actually retrieved.

4. HNSW ef_search tuning

    

      ef_search controls how many graph neighbors Chroma explores per query — higher
      means better recall at the cost of speed, and it can be changed live without rebuilding the
      index. On a 12-document toy collection the result set won't visibly change; at millions of
      vectors this is the knob that trades latency for accuracy.
